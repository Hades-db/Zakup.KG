# Zakup.KG: путь от макета к рабочему продукту

У каждого шага есть вопрос, варианты с плюсами и минусами и моя рекомендация. Работа идёт так:

1. Вы отвечаете на вопрос шага: в строке «Ваш ответ» пишете номер варианта или свой вариант.
2. Я делаю шаг и показываю результат.
3. Только после этого переходим к следующему вопросу.

Ничего не делаю, пока вы не ответили на вопрос шага.

**Ответы получены 24.11.2026.** Итоговый стек:
- приложение для Android, iOS и ПК, а также админка — Flutter (Dart), один код;
- сервер — NestJS + PostgreSQL (схема `db/`);
- файлы — MinIO; пуши — FCM; ошибки — GlitchTip;
- всё размещается на сервере в КР.

Инструкция по размещению версии для показов — `docs/DEPLOY_SHOWCASE.md`.

Что уже готово:

| Что | Где |
|---|---|
| Макет приложения (магазин, поставщик, доставщик) | `mvp.html` |
| Макет админ-панели | `admin.html` |
| Схема базы данных PostgreSQL с демо-данными и правилами | `db/` |
| Версия для показов (ПК, Android, iOS через браузер, работает без сети) | `release/` |

Данные в версии для показов хранятся только в браузере. Рабочий продукт — это сервер, база и приложения в магазинах.

## Этап Б. Рабочий продукт

### Шаг Б1. Мобильное приложение: на чём писать
**Вопрос:** какой стек для Android и iOS?

| # | Вариант | Плюсы | Минусы | Срок первой версии* |
|---|---|---|---|---|
| 1 | **Flutter (Dart)** | Один код для Android, iOS и веба (ПК). Быстрый, красивый интерфейс, легко повторить макет | Dart — менее распространённый язык. Веб-версия тяжелее обычного сайта | 6–8 недель |
| 2 | React Native (TypeScript) | Самый популярный язык, много разработчиков в регионе. Можно делить код с админкой на React | Для ПК нужен отдельный веб (React) | 6–8 недель |
| 3 | Нативно: Swift (iOS) + Kotlin (Android) | Максимальная скорость и доступ к камере | Два отдельных приложения, вдвое дольше и дороже | 12–16 недель |
| 4 | Capacitor: текущий веб-код упаковать в приложение | Самый быстрый путь, макет уже написан | Макет — один большой файл, для продукта его всё равно придётся переписать | 2–3 недели |
| 5 | Только PWA (как версия для показов), без магазинов приложений | Ничего не публиковать, обновления мгновенные | На iOS слабые пуш-уведомления, нет в App Store и Google Play, меньше доверия | 3–4 недели |

\* С учётом того, что код пишет Claude, а вы проверяете. Сервер в срок не входит.

**Предлагаю:** 1, Flutter. Одним кодом закрываем телефон и ПК, а сканер штрихкода и QR работают через готовые пакеты (`mobile_scanner`). Если важнее скорость выхода, то 4 сейчас и 1 потом.
**Ваш ответ:** 1 — Flutter (Dart)

### Шаг Б4. Сервер (бэкенд)
**Вопрос:** как делаем серверную часть? Подробное сравнение — в документе «Supabase или свой сервер».

| # | Вариант | Плюсы | Минусы |
|---|---|---|---|
| 1 | Supabase (готовые база, вход, файлы, realtime) | Быстрый старт, схема `db/` ложится почти без правок | Облако Supabase за рубежом (нужно согласие пользователей) или сложная установка на свой сервер |
| 2 | Свой сервер: Node.js (NestJS, TypeScript) | Полный контроль, сервер в КР, популярный язык | Вход, файлы и уведомления писать самим (+2–3 недели) |
| 3 | Свой сервер: Python (FastAPI) | Простой код, удобно для отчётов и Excel | Чуть медленнее Node на большом трафике (для нас не важно) |
| 4 | Свой сервер: Dart (Serverpod или Dart Frog) | Тот же язык, что и Flutter | Мало готовых решений и специалистов |
| 5 | Свой сервер: Go | Очень быстрый и экономный | Писать дольше, меньше разработчиков |

**Предлагаю:** 2, NestJS + PostgreSQL на сервере в КР. Схема базы уже готова, правила (статусы заказов, долги, блокировки) уже в базе. Сервер в КР снимает вопрос о передаче данных за рубеж (Цифровой кодекс, ст. 31 и 89).
**Ваш ответ:** 2 — NestJS (TypeScript) + PostgreSQL
