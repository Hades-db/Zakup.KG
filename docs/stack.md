# Технический стек и структура проекта

Документ для старта разработки. Стек выбран так, чтобы его было удобно вайбкодить вдвоём: один язык везде (TypeScript), минимум своего серверного кода, готовые вход, база и правила доступа.

## 1. Стек

| Слой | Что используем | Зачем |
|---|---|---|
| Приложение | **React Native + Expo**, TypeScript | Один код → веб-версия (пилот по ссылке), Android и iPhone |
| Навигация | **Expo Router** | Экраны как файлы в папке, просто для нейросети |
| Стили | **NativeWind** (Tailwind) | Цвета и размеры из прототипа переносятся напрямую |
| Данные в приложении | **TanStack Query** | Загрузка, кэш и обновление данных без ручного кода |
| Формы | **React Hook Form + Zod** | Формы и проверка ввода |
| Переводы | **i18next** | Кыргызский и русский с первого дня |
| Бэкенд | **Supabase** | PostgreSQL, вход по телефону, хранилище фото, правила доступа (RLS), realtime |
| Серверная логика | **Supabase Edge Functions** (TypeScript) | PDF-накладные, уведомления, сложные операции с заказами |
| Интеграция с 1С | Отдельный сервис на **Node.js** | Синхронизация цен, остатков и заказов (после MVP) |
| ИИ | Локальный **Qwen** на сервере | Сопоставление названий товаров разных поставщиков (после MVP) |
| Уведомления | **Expo Push**, позже WhatsApp Business API | Новые заказы, смена статуса |
| Сборка и публикация | **EAS Build** (Expo) | Сборка для Google Play и App Store без своего Mac |
| Код | **GitHub** | Этот репозиторий |

Версии: брать актуальные стабильные на момент старта и зафиксировать в `package.json`.

## 2. Окружения

| Окружение | Где | Для чего |
|---|---|---|
| **dev** | Supabase в Docker на домашнем сервере (или локально) | Разработка, эксперименты, тестовые данные |
| **prod** | Облачный Supabase (бесплатный тариф на старте) | Реальные дистрибьюторы и магазины |

Домашний сервер не используем для prod: зависимость от света и домашнего интернета, нет резервирования.

Секреты (ключи Supabase и т.д.) — только в `.env`, файл в `.gitignore`. В приложении — только публичный `anon`-ключ; `service_role`-ключ — только в Edge Functions и сервисе 1С.

## 4. Модель данных

Главная идея: всё привязано к **организации**. Организация бывает двух типов: дистрибьютор или магазин. Люди состоят в организациях с ролью.

| Таблица | Что хранит | Основные поля |
|---|---|---|
| `organizations` | Дистрибьюторы и магазины | `id`, `type` (`distributor`/`store`), `name`, `address`, `phone`, `inn` |
| `profiles` | Пользователи | `id` (= пользователь Supabase), `full_name`, `phone`, `language` |
| `memberships` | Кто в какой организации и с какой ролью | `user_id`, `org_id`, `role` (`owner`, `admin`, `agent`, `store_staff`) |
| `store_links` | Какие магазины работают с каким дистрибьютором и какой агент их ведёт | `distributor_id`, `store_id`, `agent_id`, `payment_terms`, `credit_days` |
| `categories` | Категории товаров | `id`, `name_ru`, `name_ky` |
| `products` | Товары дистрибьютора | `id`, `distributor_id`, `name`, `category_id`, `unit`, `barcode`, `photo_url`, `min_qty`, `is_active`, `external_id` (код в 1С) |
| `prices` | Цены (можно разные для разных магазинов) | `product_id`, `price`, `store_id` (пусто = общая цена), `valid_from` |
| `orders` | Заказы | `id`, `number`, `store_id`, `distributor_id`, `agent_id`, `status`, `total`, `payment_method`, `paid_at`, `delivery_date`, `created_by` |
| `order_items` | Позиции заказа | `order_id`, `product_id`, `qty`, `price` (цена на момент заказа) |
| `order_events` | История статусов | `order_id`, `status`, `user_id`, `created_at`, `comment` |
| `offers` | Новинки и акции для магазинов | `id`, `distributor_id`, `product_id`, `message`, `created_by` |
| `offer_targets` | Кому отправлена новинка | `offer_id`, `store_id`, `seen_at`, `ordered` |
| `invoices` | Накладные | `order_id`, `number`, `pdf_url`, `esf_number` (заполняется позже) |

**Статусы заказа:** `sent` (отправлен) → `confirmed` (подтверждён) → `delivering` (в пути) → `delivered` (получен) → `paid` (оплачен). Отдельно: `rejected` (отклонён), `cancelled` (отменён магазином).

**Важно:**
- В `order_items` всегда сохраняем **цену на момент заказа**, а не ссылку на текущую цену.
- Деньги храним в **тыйынах целым числом** (1 сом = 100 тыйын), а не дробными числами — так не будет ошибок округления.
- Номер заказа и накладной — по порядку внутри каждого дистрибьютора.

## 5. Правила доступа (RLS)

Самое важное для безопасности. Включить RLS на **всех** таблицах. Правила:

| Кто | Видит | Может менять |
|---|---|---|
| Владелец магазина | Свою организацию, товары и цены дистрибьюторов, с которыми связан, свои заказы, адресованные ему новинки | Создавать заказы, отменять свои заказы до подтверждения |
| Агент | Магазины, закреплённые за ним, их заказы, товары своего дистрибьютора | Подтверждать или отклонять заказы своих магазинов, создавать новинки |
| Админ дистрибьютора | Всё внутри своего дистрибьютора | Товары, цены, агентов, привязку магазинов, статусы заказов |

Правила проверки:
- Магазин **не видит** чужие магазины, их заказы и персональные цены.
- Дистрибьютор **не видит** цены и заказы других дистрибьюторов.
- Статусы меняются только по разрешённым переходам (например, нельзя из `sent` сразу в `paid`). Переходы проверяет Edge Function `create-order` / триггер в базе, а не приложение.
- Для каждой таблицы написать тест: войти пользователем другой организации и убедиться, что данных не видно.

## 6. Порядок разработки MVP

Каждый шаг — отдельная ветка и пулл-реквест. Следующий шаг начинать, когда предыдущий работает.

1. **Каркас.** Expo-проект, Expo Router, NativeWind, тема из `design/figma/README.md`, переводы ky/ru, подключение к Supabase (dev).
2. **База.** Миграции с таблицами из раздела 4, правила доступа из раздела 5, `seed.sql` с тестовым дистрибьютором, агентом, 3 магазинами и 20 товарами.
3. **Вход.** Вход по номеру телефона (SMS-код), определение роли по `memberships`, переход в нужный раздел.
4. **Кабинет дистрибьютора (веб).** Список товаров, добавление и редактирование, цены, загрузка фото, список агентов и магазинов.
5. **Магазин: каталог и заказ.** Главная, каталог, карточка товара, корзина, оформление заказа.
6. **Агент: заказы.** Входящие заказы, подтверждение и отклонение, список на доставку.
7. **Статусы и история.** Экран заказа со статусами для магазина, обновление в реальном времени.
8. **Накладная PDF.** Edge Function `invoice-pdf`, кнопка «Скачать / отправить».
9. **Новинки.** Агент или дистрибьютор отправляет новинку выбранным магазинам; магазин видит её и может заказать.
10. **Уведомления.** Push о новом заказе (агенту) и смене статуса (магазину).
11. **Проверка безопасности.** Пройтись по разделу 5, попытаться получить чужие данные.
12. **Пилот.** Перенести на облачный Supabase, собрать веб-версию, раздать ссылки.

**После MVP:** интеграция с 1С, оплата и долги (отсрочка), маршрут агента, сопоставление товаров через Qwen, публикация в Google Play, затем в App Store.

## 7. Правила для вайбкодинга

- Давать нейросети **один шаг за раз** и прикладывать нужные части этого документа и прототипа (`design/prototype.html`).
- Изменения базы — **только через миграции** в `supabase/migrations/`, не руками в панели Supabase.
- Не класть в код ключи и пароли.
- Каждое изменение — через пулл-реквест; второй человек хотя бы бегло смотрит.
- После каждого шага проверять вручную: под магазином, под агентом и под дистрибьютором.
- Если нейросеть предлагает отключить RLS «чтобы заработало» — не соглашаться, а искать ошибку в правилах.
